# 2026-08-03 뉴스브리핑 지연 사후분석

## 결론

오늘 지연의 직접 원인은 OpenAI 잔액 부족이 아니었다. 05:34 KST 사전점검에서
OpenAI, Naver, Kakao가 모두 정상임을 확인한 뒤에도, 06:05 KST 1차 실행이 느린
언론사 원문을 너무 많이 크롤링하면서 대부분의 실행 시간을 소비했다. 이후
OpenAI 요약 단계까지 도달했지만 GitHub Actions의 25분 제한으로 06:31 KST에
취소되어 Kakao 전송을 시도하지 못했다.

OpenAI 크레딧 충전은 별도 문제였다. 7월 29일과 30일 사전점검에서 실제로
`HTTP 429 / insufficient_quota / no credits remaining`이 확인되었다. 다만 일일
배포 코드는 OpenAI를 사용할 수 없을 때 결정론적 요약으로 내려갈 수 있으므로,
충전은 AI 요약·편집 품질 복구에는 필요했지만 기본 배포의 필수조건은 아니었다.
기존 사전점검이 이 차이를 구분하지 않고 전체 실패로 표시한 것이 운영 판단을
과도하게 만들었다.

## 영향

- 정상 06시대 배포 목표보다 지연됐고, 07:00 마감 6분 48초 전인 06:53:12에
  간신히 전송을 완료했다.
- 저장된 스냅샷을 사용한 무-OpenAI 복구본이 06:53:12 KST에 처음 전송되었다.
- 첫 복구본의 편집 품질 점수는 51.9점으로, 중복 기사·홍보성 기사·약한 선별이
  포함되었다.
- 수동 교정 후 게시 페이지는 운영 품질 93.42점, 독자 품질 90.54점의 최종본으로
  교체했다.

## OpenAI 크레딧 재분석

확정 가능한 사실은 다음과 같다.

1. 7월 29일과 30일 사전점검은 OpenAI의 실제 잔액 소진 응답을 받았다.
2. 충전 후 8월 2일 19:00 KST 수동 점검과 8월 3일 05:34 KST 예약 점검은
   모두 성공했다.
3. 오늘 1차 실행에는 quota 오류가 없었다. 따라서 오늘 지연은 충전 실패나 잔액
   부족으로 발생한 것이 아니다.
4. 7월 27일에는 실패한 일일 실행이 여러 차례 반복됐고, 각 실행이 전체 편집평가와
   보정 제안을 다시 호출할 수 있었다. 저장된 평가 1회의 예시만 해도 52,081
   토큰, 추정 비용 0.38445달러였다. 이 반복 실행은 잔액 소진의 유력한 원인이다.
5. 다만 잔액이 전부 사용돼 소진된 것인지, 선불 크레딧 유효기간 만료가 함께
   있었는지는 OpenAI 결제 원장 없이는 확정할 수 없다.

## 근본 원인

### 1. 배포 경로에 시간 예산이 없었음

원문 크롤링은 500건이 넘는 기사에 대해 느린 사이트 타임아웃과 재시도를 그대로
기다렸다. 본문 보강은 품질 향상 기능인데도 필수 배포 경로 전체를 지연시켰다.

### 2. OpenAI 재호출 상한이 너무 컸음

요약 요청은 최대 70초와 3회 재시도를 사용할 수 있었고, 모델이 이미 반환했지만
로컬 품질 검사에서 탈락한 행도 누락 행처럼 다시 호출했다. 편집평가·보정 역시
한 실행에서 여러 차례 이어질 수 있었다. 이는 지연과 크레딧 사용량을 동시에
늘렸다.

### 3. 복구가 정상 경로의 비싼 단계를 반복했음

마감 복구는 빠른 결정론 경로여야 했지만, 기존에는 OpenAI 요약과 전체 원문 수집을
다시 실행할 수 있었다.

### 4. 워치독이 이전 실패를 고려하지 않았음

워치독은 가장 최신 실행이 동작 중이면 기다렸다. 바로 앞의 1차 실행이 이미
실패했다는 사실과 07:00까지 남은 시간을 함께 판단하지 못했다.

### 5. 필수 API와 선택적 품질 API의 상태를 구분하지 않았음

Naver와 Kakao는 기본 수집·전송에 필수지만 OpenAI는 품질 향상 기능이며 안전한
결정론 fallback이 있다. 사전점검이 OpenAI quota 부족도 전체 실패로 처리해 충전이
배포의 필수 전제처럼 보이게 했다.

### 6. 스냅샷 복구의 품질검사 순서와 사건 지문에 빈틈이 있었음

일반 일일 실행은 품질검사 후 게시·전송하도록 되어 있었지만, 저장 스냅샷 복구는
페이지와 Kakao를 먼저 전송한 뒤 워크플로의 다음 단계에서 편집평가를 수행했다.
또한 사건 중복 지문이 시·군·구는 인식하면서 `경북도` 같은 광역도를 인식하지
못해, 같은 1,433억원 스마트 APC 사업을 다룬 다매체 기사 5건이 서로 다른 사건처럼
남았다.

## 적용한 재발 방지책

- 원문 크롤링을 섹션별 균형을 유지한 상위 120개 URL로 제한하고, 연결 3초·읽기
  7초·재시도 0회로 제한했다.
- 일반 일일 실행의 OpenAI 요약을 요청당 45초·1회로 제한했다.
- 모델이 반환했지만 품질 검사에서 탈락한 요약은 재호출하지 않고 결정론 요약을
  사용한다. 실제 누락 행만 최대 5개 재시도한다.
- 일반 일일 실행의 편집 보정을 최대 1회 적용·2회 제안으로 제한했다. 운영자가
  명시적으로 실행한 품질 복구만 기존의 넓은 예산을 사용한다.
- 강제 SLA 복구에서는 OpenAI 요약과 편집평가를 모두 생략하고 동일한 안전 게이트를
  통과한 결정론 요약만 배포한다.
- 워치독은 06:30 이후 이전 기본 실행이 실패했고 새 기본 실행이 동작 중이면, 새
  실행이 오래되지 않았더라도 취소하고 즉시 강제 복구한다.
- OpenAI quota 부족은 사전점검을 실패시키지 않고 `AI 품질 저하 / 기본 배포 준비됨`
  으로 표시한다. Naver 또는 Kakao 실패만 배포 준비 실패로 처리한다.
- 배달 영수증이 있으면 중복 실행과 중복 Kakao 전송을 차단한다.
- 구독자에게 전송하는 스냅샷 복구는 편집 품질검사를 Kakao보다 먼저 강제한다.
  편집검사가 실패·타임아웃하거나 기준을 통과하지 못하면 브리핑은 보내지 않고
  보류 알림만 전송한다. 이 경로에서는 느슨한 SLA fallback도 허용하지 않는다.
- 전국 17개 시·도의 정식명·약칭을 같은 지역 지문으로 정규화해 `경북도`·`경북`·
  `경상북도` 스마트 APC 보도를 동일 사건으로 제거한다.
- 복구용 사전 편집검사도 호출당 45초·1회, 보정 1회·제안 2회로 제한했다.

## 검증 기준

- 일반 실행이 실패해도 06:30~06:35 워치독이 무-OpenAI 복구를 시작해야 한다.
- OpenAI quota가 0이어도 결정론 요약과 안전 게이트로 기본 브리핑을 배포할 수
  있어야 한다.
- 일반 실행에서 원문 크롤링과 OpenAI 재시도가 정해진 상한을 넘지 않아야 한다.
- 같은 날짜의 성공 영수증이 있으면 추가 실행이 외부 호출이나 Kakao 전송을
  반복하지 않아야 한다.
- 스냅샷 복구에서 품질검사가 Kakao 게시보다 먼저 실행되어야 한다.
- 2026-08-03 실제 스냅샷 재배치에서 스마트 APC 기사는 5건이 아니라 1건만
  남아야 한다.

검증 결과, CI 회귀 테스트 333개가 통과했고 2026-08-03 실제 스냅샷 로컬 재배치에서
스마트 APC 기사가 1건만 남았다.
